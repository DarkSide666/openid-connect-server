# Error Handling, Logging and Operations

This document reviews the existing DarkSide OpenID Connect Server components and the standalone reference provider from an operational perspective. It describes the responsibilities of a host application; it does not add protocol capabilities or prescribe a particular framework, logger, monitoring service or deployment platform.

The library is framework-independent and does not depend on PSR-3. It returns protocol responses where its endpoint handlers own the response, and it allows unexpected application or infrastructure failures to propagate to the host application's exception middleware. The host application must therefore provide the final HTTP error boundary, logging, monitoring and operational controls.

## 1. Error-handling boundary

There are two broad classes of failure, and they must not be handled the same way.

### Expected protocol errors

Examples include invalid client authentication, an invalid or expired authorization code, an unsupported grant, an invalid access token, and insufficient scope. These are part of normal protocol operation. Preserve the OAuth/OIDC status code, response body and protocol headers generated by League OAuth2 Server or by the library's endpoint handler. Do not turn an expected OAuth error into an unstructured application error page or a generic `500` response.

The library's `UserInfoEndpoint` currently handles these cases directly:

- Unsupported HTTP methods return `405` with `Allow: GET, POST`.
- Invalid Bearer-token validation returns League's OAuth error response.
- A valid token without the `openid` scope returns `403` with `insufficient_scope`.
- A token without the required end-user or client identifier returns `403` with `access_denied`.
- Successful responses return JSON and disable caching.

The authorization and token endpoints are normally delegated to League OAuth2 Server. The host should preserve the responses generated by `OAuthServerException::generateHttpResponse()` rather than replacing their protocol semantics.

### Unexpected application or infrastructure failures

Examples include database or cache outages, a failed metadata-store operation, a missing or unreadable key file, malformed identity data, an exception in the identity resolver, and an unexpected programming error.

These failures should:

1. Be caught at the host application's outer HTTP exception boundary.
2. Produce a generic client-facing `500 Internal Server Error` response (or an appropriate temporary-unavailability response when the host can reliably identify that condition).
3. Be logged internally with the exception and stack trace, subject to secret and personal-data redaction.
4. Include a request/correlation identifier so operators can connect the response to the internal log event.
5. Never expose filesystem paths, SQL errors, stack traces, key material, credentials or internal class details to the client.

Do not catch every `Throwable` inside the library and convert it into an OAuth error. Doing so would blur the distinction between protocol failures and server faults, and could conceal conditions that operators need to investigate.

## 2. What the current implementation does

The following observations are based on the code in this repository snapshot.

| Area | Current behavior | Operational implication |
|---|---|---|
| UserInfo protocol failures | `UserInfoEndpoint` returns protocol-oriented responses for token validation, scope and identifier failures. | Preserve these responses in the host router. |
| UserInfo application failures | Exceptions from identity resolution, claim validation or JSON encoding are not converted into protocol errors by the endpoint. | The host exception middleware must handle unexpected failures safely. |
| OAuth authorization/token errors | The reference routes catch `OAuthServerException` and use League's generated HTTP response. | Do not replace League's OAuth response body/status with a generic response. |
| Reference-provider unexpected errors | Slim error middleware is configured with error-detail display disabled, error logging enabled and detailed error logging disabled. | Keep detailed errors out of HTTP responses; explicitly configure and monitor the production logger in the real host application. |
| Startup configuration | The reference `ProviderFactory` validates required configuration and reads key material before the routes are served. | Startup should fail closed if required keys or configuration are missing or invalid. |
| Health endpoint | `/health` returns a simple test-provider status after the provider services have been constructed. | It is a basic process/application check, not a comprehensive production dependency or synthetic-login check. |

The reference provider is a test fixture. Its error middleware, file-backed repositories, health route and operational configuration are examples, not production-ready operational components.

## 3. Logging responsibilities

The library intentionally has no logger dependency and does not emit log records itself. A host application should log at the boundaries where it has the necessary request, client and operational context.

Useful events include:

- Provider startup success and failure.
- Configuration validation failures.
- Signing-key load or validation failures, including the configured `kid` but never key contents.
- Authorization and token endpoint failures, classified by protocol error code and HTTP status.
- Metadata-store, client repository, access-token repository and identity-resolver failures.
- User authentication failures and account-state decisions, according to the application's audit policy.
- Signing-key rotation activation and retirement.
- Readiness transitions, dependency outages and recovery.

Use structured fields where possible: timestamp, severity, event name, request/correlation ID, endpoint, HTTP status, protocol error code, duration and a deployment/environment identifier. Include a client identifier or key ID only where operationally useful and permitted by the application's privacy policy.

### Never log secrets or bearer credentials

Do not log:

- Client secrets or client-authentication headers.
- Passwords, login form bodies or session cookies.
- Authorization codes, access tokens, refresh tokens or complete ID Tokens.
- The `Authorization` request header or raw token endpoint request body.
- Private signing keys, encryption keys or their PEM contents.
- OIDC nonces or PKCE code verifiers.
- Full UserInfo responses or unnecessary personal claims.

Treat subject identifiers and user identifiers as sensitive or pseudonymous data. If they are required for an audit use case, apply access controls, retention limits and the application's privacy requirements. Prefer a stable internal audit reference or a keyed pseudonym over recording raw identity data in general application logs.

Logs should be access-controlled, centrally collected where appropriate, protected against tampering, monitored for ingestion failures and retained according to a documented policy. Avoid logging the same exception at every layer; log it once at the boundary that can attach the request context and then propagate or return the response.

## 4. HTTP response caching

Cache policy is applied by the host HTTP layer, not by the library's discovery or JWKS generators. The `UserInfoEndpoint` itself applies `Cache-Control: no-store` and `Pragma: no-cache` to its successful JSON responses and its Bearer-token validation error responses.

Use the following policy as a baseline:

| Response | Recommended policy | Reason |
|---|---|---|
| Token endpoint responses | `Cache-Control: no-store` and `Pragma: no-cache` | Contains bearer credentials and other sensitive token material. |
| UserInfo responses | `Cache-Control: no-store` and `Pragma: no-cache` | Contains user claims and depends on an access token. |
| Login, authorization and consent pages | `Cache-Control: no-store` | May contain session-specific or security-sensitive interaction state. |
| Discovery metadata | Public caching may be used with a controlled, relatively short freshness lifetime. | Metadata is public, but endpoint/configuration changes must propagate predictably. |
| JWKS | Public caching may be used with a deliberately bounded `max-age`. | Avoids unnecessary key fetches while keeping rotation and key-retirement windows manageable. |
| Health/readiness responses | Usually `no-store` or a very short lifetime. | Monitoring should observe current state, not a stale cached result. |

The reference provider currently uses a shared JSON response helper that applies `no-store` to discovery, JWKS, health and test-control JSON responses as well as other JSON responses. This is conservative and safe for a local test fixture, although it prevents clients and intermediaries from caching public discovery/JWKS data. It is not a cache policy imposed by the library itself.

If a production host enables JWKS caching, coordinate the cache lifetime with signing-key rotation. Keep an old public key published for at least the maximum lifetime of tokens signed with it, plus accepted clock skew and the maximum JWKS cache/propagation delay. Publish the new key before relying on it for newly signed tokens when the deployment requires a pre-publication period. Do not remove an old public key merely because the active signing key has changed.

Never allow a CDN, reverse proxy or application cache to override `no-store` on token or UserInfo responses. Verify the headers at the public edge, not only in an application unit test.

## 5. Health checks, readiness and startup

A production provider should distinguish at least:

- **Liveness:** Is the process running and able to serve requests? A liveness failure may justify restarting the process.
- **Readiness:** Can this instance safely serve protocol traffic? Readiness should fail when required configuration, signing keys, repositories or other mandatory dependencies are unavailable.
- **Synthetic protocol check:** Can an external monitor retrieve discovery metadata and JWKS over the expected public HTTPS origin? A controlled synthetic client can additionally exercise a complete login/token flow in a non-production test environment.

Do not expose detailed dependency status, filesystem paths, database names or exception messages in a public health response. Keep detailed diagnostics in protected monitoring and logs.

Startup should validate required configuration and key material before accepting traffic. Fail closed on missing or unreadable keys, mismatched key pairs, invalid issuer/endpoint configuration or unavailable mandatory persistence. Avoid starting in a partially configured state and waiting for the first real user request to reveal the problem.

For multi-instance deployments, verify that all instances share consistent client configuration, signing-key state, authorization-code metadata semantics and revocation state. A local file lock is not a distributed coordination mechanism.

## 6. Operational controls owned by the host

The host application and deployment platform remain responsible for:

- HTTPS at every public protocol endpoint and correct proxy/TLS configuration.
- Secure session cookies, CSRF protection and login/consent protections.
- Rate limiting and abuse detection, especially for login and token endpoints.
- Audit logging, monitoring, alerting and incident response.
- Secret management and private-key file permissions or external key custody.
- Backups, restoration tests and persistence availability.
- Clock synchronization across application instances.
- Safe deployment and rollback of configuration and signing-key changes.
- Monitoring of discovery, JWKS, token and UserInfo availability and latency.
- Review of cache headers after reverse proxies/CDNs have applied their rules.

The library does not provide these operational services and should not be represented as doing so.

## 7. Deployment verification checklist

Before exposing a provider to real relying parties, verify at the public HTTP boundary:

- [ ] Invalid client credentials produce a protocol error without leaking internal details.
- [ ] Invalid authorization codes, PKCE verifiers and Bearer tokens produce the expected protocol responses.
- [ ] Unexpected repository and identity-resolver failures produce a generic server response and a useful internal log event.
- [ ] No response exposes stack traces, filesystem paths, SQL errors, private keys or credentials.
- [ ] Token and UserInfo responses carry `Cache-Control: no-store` and `Pragma: no-cache`.
- [ ] Login and authorization pages are not cached.
- [ ] Discovery and JWKS cache policies are intentional and compatible with the key-rotation runbook.
- [ ] Logs contain correlation IDs and operational context but no tokens, secrets, passwords, nonce values or PKCE verifiers.
- [ ] Liveness and readiness behavior is documented and monitored.
- [ ] Startup fails closed when required configuration, key material or persistence is unavailable.
- [ ] Rate limits, alerting, log retention and incident-response ownership are in place.
- [ ] Multi-instance persistence and revocation behavior have been tested under concurrent requests.

Passing this checklist is deployment-specific evidence, not OpenID Connect certification. A production deployment still requires a security review appropriate to its threat model and infrastructure.
